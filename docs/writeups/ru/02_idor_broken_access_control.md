# 02. IDOR / Broken Access Control

## Суть

Пользователь видит только свои заметки в списке, но endpoint `/note?id=...` не проверяет владельца заметки. Это классический IDOR: объект выбирается по предсказуемому идентификатору, а authorization check отсутствует.

## Как воспроизвести

1. Войдите как `alice / password123`.
2. Откройте:

```text
http://127.0.0.1:8090/note?id=3
```

3. Вы увидите заметку пользователя `bob`.

[HTTP-тест](../../../tests/test_http.py) входит под Alice и проверяет, что в
ответе есть заметка Bob и указано имя её владельца.

## Где проблема в коде

Функция `get_note_vulnerable()` в `vuln_notes/database.py` параметризованно
выбирает заметку только по `id`, но не связывает её с текущим пользователем:

```python
WHERE notes.id = ?
```

В запросе нет условия:

```sql
AND notes.owner_id = ?
```

## Impact

Любой авторизованный пользователь может читать приватные заметки других пользователей, перебирая `id`.

## Как исправить

[Исправленный запрос](../../../vuln_notes/database.py) одновременно
проверяет идентификаторы заметки и её владельца:

```sql
SELECT ...
FROM notes
WHERE notes.id = ? AND notes.owner_id = ?
```

ID пользователя берётся из проверенной сессии. Для чужой и несуществующей
заметки запрос одинаково возвращает пустой результат. Доступ администратора,
если он предусмотрен, требует отдельного правила авторизации.

[Регрессионные тесты](../../../tests/test_database.py) проверяют, что Alice
не может прочитать заметку Bob, а Bob может открыть эту же заметку. Alice
сохраняет доступ к своей заметке. Альтернативное представление ID не
позволяет обойти проверку владельца.

```sh
python3 -B -m unittest discover -s tests -k idor -k owner_scoped -v
```

HTTP-маршрут учебного приложения сохраняет уязвимое поведение для
воспроизведения. Исправленный запрос проверяется на уровне доступа к данным.
Неподписанная сессия в лаборатории — отдельный учебный сценарий. Для
реального маршрута нужна доверенная сессия.
